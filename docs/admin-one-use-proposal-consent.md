# One-use human confirmation for an exact worker pairing proposal

**Status: source-only, feature OFF, no public route, no live Cloudflare enrollment.** Parent [Command Center Issue #30](https://github.com/jan2xo/bke-command-center/issues/30), following merged Command Center #39–#50 and Worker #104.

## Problem and intent

PR #50's atomic pairing invitation already binds a proposed device key, unique ChatGPT target, browser profile, bridge identity and worker ID, but leaves the **actual human confirmation of that exact proposal** to a trusted server callback that is not yet implemented. A boolean from a browser or a repeatable POST must not become consent. This independent dependency adds a durable, **60-second, one-use proposal-confirmation challenge** with a server-only consumption API designed to be called INSIDE the future atomic issuance transaction, not as a standalone approval grant.

## Security boundary

`createAdminProposalConsent` is a dormant server-only factory. It requires current PREPRODUCTION, Access-policy verification, Admin pairing action flag and a separate new `BKE_ADMIN_PROPOSAL_CONSENT_ENABLED=true` switch. That switch is **not in Wrangler**. No actual `src/index.js` route or Cloudflare Durable Object RPC invokes this module.

`present({worker_id,proposal_sha256,env,executionCtx})` takes a **trusted backend-computed SHA-256 proposal** of the complete #50 installation/worker/public-P-256-key/resource set; it must not be a browser-supplied or stale digest. It authorizes the human through Cloudflare's platform-provided `executionCtx.access` with exact application AUD and Admin allowlist and a separately injected trusted `authorizeSubject` function. That function must derive the SAME stable, opaque **HMAC-keyed human subject SHA-256** used in the #48 protected pairing RPC, from the authenticated human identity. It must never trust `authorized:true`, forwarded JWT/user email headers, unsalted email SHA256 or an arbitrary browser-supplied subject. The module validates the 64-character result but does not implement or attest the callback's underlying human identity derivation. This remains a separately certified integration requirement.

Inside the existing single-installation `store.atomic`, `present` creates one unique 256-bit CSPRNG challenge ID (60s TTL) with worker/proposal digest/keyed subject and `PENDING` status in the new fixed **`bke:pairing:v1:consents`** key. The bounded/shape-checked JSON registry has at most 100 records and refuses duplicate IDs, conflicting live proposals for one worker, corrupted or ambiguous storage, and unsupported key access. Only the opaque challenge, worker and exact proposal SHA256 are eligible to leave the **trusted server** for a future human approval presentation. The actual UI must display the human-readable worker/key/target/profile/resource proposal **alongside** the digest; showing only a digest would not constitute meaningful human understanding. There is NO UI in this intent.

`confirm({request,env,executionCtx})` accepts only a strict **POST** to the fixed future path `https://cc.jl-bke.com/api/admin/pairing/confirm-proposal`, with same-origin `Origin`, matching `sec-fetch-site=same-origin` and allowed Fetch Metadata mode, JSON-only at most 1024 bytes and no content encoding or query. It requires exact fields `action=pair`, human-typed `confirm_worker_id` matching `worker_id`, challenge ID and *identical* proposal digest. It verifies platform human Access **before** parsing any request body, independently rederives the keyed subject, and transactionally changes precisely one `PENDING` record to `CONFIRMED`. A replay, wrong human, worker, proposal, action, origin, method or expired challenge fails closed. This is a contract to be used later by a real Admin POST handler, NOT a currently reachable endpoint.

`consumeInTransaction(tx,{challenge_id,worker_id,proposal_sha256,subject_sha256})` does **not** create its own transaction. It verifies the unique still-valid `CONFIRMED` record and marks it `CONSUMED` using the **existing caller transaction**. A future wiring PR MUST call it within PR #50's same atomic transaction that writes the signed device challenge and the 90s Admin ticket. This design prevents consumed approval on a failed invitation: if any later pairing issuance write or callback fails, the consent transition also rolls back. A separate transaction calling this method without the actual invitation write is forbidden and NOT certified as a final authorization.

## Scope and certification

- New fixed `consents` key extends the existing bounded installation-scoped SQLite Durable Object adapter; it is not a planner, PR task record, device credential or active-worker lease.
- Sixteen Node tests cover valid confirmation/consumption, CSRF/origin/method/extra-field denial, platform human mismatch, cross-worker/proposal mismatch, TTL, replay, simultaneous requests, malformed registry, invalid entropy, storage rollback and inactive feature flags.
- The actual local Cloudflare Workerd/SQLite smoke fixture now checks **four** keys (paired/pending/admin_actions/consents) for persistence, isolation, atomic rollback and concurrent writes. The fixture remains localhost-only and disconnected from the real Command Center deployment.
- Required certification is full **exact-head** Command Center `ci`: `npm ci`, all Node tests, syntax checks, Wrangler PREPRODUCTION dry-run and local Workerd SQLite smoke, plus bounded security review and SHA-locked source-only merge.

## Explicitly still locked

The trusted proposal-rendering UI, real Cloudflare Access/CSRF human confirmation route, cryptographically keyed subject derivation adapter, actual authenticated device challenge submission, and **atomic linkage to PR #50's invitation issue operation** are not yet wired. Do not treat `CONFIRMED_FOR_ATOMIC_ISSUANCE` as pairing authority; do not serialize sensitive human ticket nonces from PR #50 to browsers or devices. GitHub PR inventory is NON_ATOMIC_ENUMERATION and cannot reserve workers or browser profiles. No Cloudflare PREPRODUCTION/production deploy, secret changes, GitHub App permission expansion, live device pairing, worker lease, wake, OAuth/MFA/CAPTCHA automation or parked Android #90 continuation is authorized by this source-only PR.

Next separate intent: link a trusted Access-derived subject + actual one-use proposal consent to the **same invitation issuance transaction**, then independently certify human-origin POST/CSRF and device-only challenge transport before authorized PREPRODUCTION live acceptance. GitHub is engineering truth, PR is delegation/ledger, Worker is liveness.
