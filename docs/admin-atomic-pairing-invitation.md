# Atomic human-confirmed pairing invitation — source-only

**Status: DORMANT, no public HTTP route or callable Durable Object issuance RPC.** Parent [Command Center Issue #30](https://github.com/jan2xo/bke-command-center/issues/30); builds on merged #39–#49. Github stays the sole PR/task/worker ownership source of truth; DO stores only bounded pairing state.

## Independent source intent

Existing #40 device challenges and #44 one-use human action tickets can each be issued in their own storage transactions, leaving an orphaned device challenge if human issuance fails, or the reverse. `createAtomicPairingInvitation` issues both proofs inside the SAME existing installation-scoped `ctx.storage.transaction`, writing `pending` and `admin_actions` as one all-or-nothing operation. It reuses the existing paired/pending/ticket validators, the strict private GitHub App PR-inventory parser and `evaluateWorkerEnrollment` resource-collision policy. It does not create a second task database.

It requires all existing PREPRODUCTION / Access policy / approved PR-inventory / Admin pairing action / protected-pairing latches and a **new independent** `BKE_ADMIN_PAIRING_ISSUANCE_ENABLED=true` latch. This flag is absent from Wrangler and NO live route/DO method imports the issuance factory.

An injected **trusted server-only** `readInstallationInventory()` callback must obtain a fresh, complete, minimally-scoped GitHub App inventory. The parser independently rejects unknown fields, inconsistent repository IDs, duplicate claims, malformed heads and permission-elevation data. The parsed `trusted_installation_id` must EXACTLY match the installation-scoped DO instance identifier (the instance ID cannot originate from browser/device input). `NON_ATOMIC_ENUMERATION` remains evidence, NOT a GitHub worker claim. Pre-existing candidate assignment, pending worker conflict, duplicate ChatGPT/browser profile/bridge/device key, damaged database or broker failure rejects issuance.

A second injected **trusted server-only** `authorizeHumanAction(proposal,platformContext)` callback must prove platform-verified human Cloudflare Access, allowlist and **explicit confirmation of the entire presented pair/worker/public-key/resources proposal**. The proposal includes a canonical SHA-256 digest of installation, worker ID, public P-256 key hash and all three resource fingerprints. The callback returns the SAME opaque keyed SHA-256 human subject that is used by the protected #48 RPC, and it MUST NOT accept browser-supplied `authorized:true`, a raw email, or a bare unsalted email hash. **This source-only module does not implement that callback nor claim real Access/consent certification**.

WebCrypto validates the canonical P-256 public JWK and generates independent random fields: 24-byte device challenge ID, 32-byte device nonce, 16-byte human-ticket ID and 32-byte human-ticket nonce. The device-signed message retains the exact already-certified `bke-command-center/preproduction/worker-pairing/v1` 120-second contract. The human ticket retains the original `bke-command-center/preproduction/admin-action/v1` 90-second digest contract. Inside one storage transaction the module validates all three registries and current resource uniqueness, rejects pending/competing worker actions and writes both pending device challenge and human ticket; any error rolls back BOTH writes. Concurrency permits independent workers with isolated fingerprint resources but never two active invitations for one worker.

The result is `ISSUED_FOR_SECURE_DELIVERY` carrying a **server-side-only** device challenge and one-time human confirmation nonce. **NEVER serialize this entire object to a browser, device, GitHub PR/comment, telemetry, or a queue.** The device must receive only its own challenge through a separately certified authenticated device channel. The human nonce must remain within an independently consented/Admin-authorized finalization path. The two proofs are not secret bearer credentials for active worker access, do not prove device key possession until signature verification, and are NOT an active lease or PR reservation. No reusable human nonce is stored in the durable registry.
